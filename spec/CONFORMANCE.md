# PBZ conformance

This page defines example stores and the expected validation results for the
[format 0.5 specification](README.md). `pbz validate` and
`pixi run validate-dataset` check these results.

## Run and inspect the examples

From the repository root, using the existing project environment:

```sh
pixi run python spec/examples.py
```

The command creates temporary Zarr v3 stores and verifies the valid examples
through native Xarray. Add `--output /path/to/new-directory` to keep the stores
and a `manifest.json` describing expected PBZ outcomes. The destination must not
already exist. The manifest is fixture documentation outside the PBZ stores;
it is not format metadata.

The script also makes invalid stores. The Rust `check_dataset` example checks
their results. Some invalid stores still open in Xarray, because PBZ adds
genomic rules that Xarray does not check.

## Canonical example

The small fixture uses reference lengths `[5, 7]`, samples `sample_1` through
`sample_3`, and thresholds `[5, 10]`. Position offsets are `[0, 5, 12]`.

| Array | Dimensions | Shape | Logical values/type |
| --- | --- | --- | --- |
| `contig_id` | `contig` | `[2]` | `chr1`, `chr2` |
| `contig_length` | `contig` | `[2]` | signed 64-bit integers `[5, 7]` |
| `sample` | `sample` | `[3]` | string dimension labels |
| `threshold` | `threshold` | `[2]` | integer dimension labels `[5, 10]` |
| `depth` | `position, sample` | `[12, 3]` | unsigned 16-bit measurements |
| `callable` | `position, sample, threshold` | `[12, 3, 2]` | Boolean `depth >= threshold` |
| `callable_count` | `position, threshold` | `[12, 2]` | unsigned 64-bit sum over samples |
| `coverage` | `bin_4, sample` | `[4, 3]` | independently supplied floating values |
| `signal` | `bin_6, sample` | `[3, 3]` | independently supplied floating values |
| `mean_depth` | `sample` | `[3]` | floating summary |
| `total_callable_count` | none | `[]` | unsigned 64-bit scalar |

Only the first four arrays are coordinates. Readers find them by name
(`contig_id`, `contig_length`) and by an array name that equals its only
dimension (`sample`, `threshold`). They do not read the Xarray `coordinates`
attribute. Neither `position`, `bin_4`, nor `bin_6` has a stored coordinate
array. Track names and calculations are examples, not reserved schema terms.

For `bin_4`, the ordered intervals are:

| Row | Contig | Start | Stop |
| --- | --- | --- | --- |
| 0 | chr1 | 0 | 4 |
| 1 | chr1 | 4 | 5 |
| 2 | chr2 | 0 | 4 |
| 3 | chr2 | 4 | 7 |

There are four bins, not `ceil(12 / 4) = 3`. `bin_6` independently has three
rows: chr1 `[0,5)`, chr2 `[0,6)`, and chr2 `[6,7)`. A reader cannot infer how the
stored numbers were computed from their dimension name.

## Valid stores generated by the script

| Fixture | Required interpretation |
| --- | --- |
| `cohort` | All the canonical variables coexist in one Dataset. Counts, dimensions, labels, and scalar values round-trip. |
| `no-coordinates-attribute` | The canonical store with every `coordinates` attribute removed. It classifies and reads the same as `cohort`. |
| `with-md5` | The canonical variables plus the optional `contig_md5(contig)` string array. |
| `non-genomic` | Sample summaries and a scalar retain root reference coordinates even without genomic variables. |
| `zero-length-contigs` | Lengths `[0,5,0]` contribute five positions and two `bin_4` rows. Zero-length contigs contribute no rows. |
| `empty-reference` | An empty reference permits zero-length genomic axes; it is distinct from a missing reference. |
| `regional-fill` | A new track has all twelve positions, selected values at flat rows `[2,4)`, and ordinary zero fill elsewhere. No shortened genomic axis is stored. |
| `values-and-missingness` | Zero stays zero without a missing sentinel; integer sentinel `-1` decodes as missing. Signed/unsigned integers above `2**53` retain exact values when no missing decoding is requested. |

Zero-length and empty-reference fixtures test the limits of the reference rules.
A particular windowing operation may still reject them with a specific operation
error; that does not make their stored reference invalid.

## Validation responsibilities

Validation should distinguish these outcomes:

1. **Invalid PBZ store:** recognized format, but an invariant below is violated.
2. **Unsupported format version:** this reader does not know that version's
   contract. Do not read it as format 0.5, and do not convert it.
3. **Unsupported encoding or operation:** the schema permits the array, but the
   implementation cannot decode it or perform the requested command. This does
   not make the store malformed.

Opening for inspection can catalog an unsupported measurement from metadata.
Reading another supported track need not fail because of it. Unsupported
reference or required coordinate encodings block the interpretations that need
them. A complete conformance check must report any content it could not inspect;
it cannot claim full validity by silently skipping unknown encodings.

### Root metadata

Apply [root-attributes.schema.json](root-attributes.schema.json) to the root
attribute object, not the entire `zarr.json` document. Validate the containing
group and array metadata against Zarr separately.

| Rule | Store check |
| --- | --- |
| R1 | Root is a Zarr v3 group with the recognized convention UUID and encoding version. |
| R2 | The direct root arrays `contig_id` and `contig_length` exist. |
| R3 | Classification uses array names and dimension names only. The Xarray `coordinates` attribute has no PBZ meaning, and its absence changes nothing. |

### Reference

| Rule | Store check |
| --- | --- |
| R4 | `contig_id` is a 1D string array on the dimension `contig`. Values are unique, nonempty, nonmissing strings. |
| R5 | `contig_length` uses a signed/unsigned integer storage encoding, not Boolean or floating storage, on the dimension `contig`. There is one length per name. |
| R6 | Interpreted lengths are exact, nonmissing, nonnegative integers. Each length and the total fit signed 64-bit indexing. Derive offsets in stored contig order. |
| R7 | If `contig_md5` exists, it is a 1D string array on the dimension `contig`. |

R5 concerns physical encoding; R6 concerns meaning. A decoder promoting an
integer array because of an unused missing sentinel does not by itself change
validity. It must not round a length or turn it into a missing value. The portable
reference fixtures use no masking or scaling metadata, so integer lengths stay
exact without that decoding complication.

### Dimensions and genomic axes

| Rule | Store check |
| --- | --- |
| D1 | Every non-scalar array has one nonempty, distinct, non-null `dimension_names` entry per axis. Scalar shape `[]` permits absent `dimension_names` or `[]`. |
| D2 | All arrays using a dimension agree on its extent. The root owns one shared coordinate identity for that dimension. |
| D3 | Every non-genomic dimension other than `contig` has a same-named 1D coordinate of matching length with unique, nonmissing string or numeric labels after supported decoding. `contig_id` labels `contig` (R4). |
| D4 | Other non-genomic root arrays may repeat values; D3's uniqueness rule does not apply to them. Names cannot collide. |
| G1 | Reserved genomic dimensions are `position` and canonical `bin_[1-9][0-9]*`; other uses of the `bin_` prefix are invalid. |
| G2 | `position` extent is `sum(lengths)`. Each `bin_N` extent is `sum(ceil(length / N))`, computed per contig with checked integer arithmetic. |
| G3 | A genomic array has exactly one genomic dimension, first. Such an array is a track. |
| G4 | Do not persist same-named coordinate arrays for `position` or `bin_N`. Runtime indexes must be removed when writing the core layout. |

`bin_1` is valid and remains distinct from `position` as a named dimension even
though both describe the same base intervals. They may occur on different
variables in one store. G3 prevents putting both on the same variable.

### Values and encodings

The format does not define a codec registry, and it does not require every
reader to support every standard encoding.

For the initial portable fixtures:

* Logical Boolean values use Xarray's `int8` plus `dtype="bool"` encoding, without
  a missing sentinel. Check the logical values as well as the physical dtype.
* Integer `_FillValue=-1` masks that sentinel; the physical Zarr `fill_value=0`
  is independently an ordinary zero. Stored and decoded dtypes can differ.
* Numeric coordinate labels and reference lengths have no missing declarations.
* Xarray's generated Zarr v3 bytes/string codecs and Zstd are used as recorded in
  each array's metadata; their defaults are not mandated PBZ storage defaults.
* A scalar's absent `dimension_names` is intentional native Xarray output.

Masked logical Booleans are not part of this initial interoperability profile.
A diagnostic on Xarray 2025.12.0 found that `int8 [0,1]` with `dtype="bool"` and
`_FillValue=0` decoded to `[True,True]`. Supporting that combination requires a
defined missing-Boolean representation and matching reader behavior. It must
not be advertised as supported or silently treated as ordinary integer data.
This is an encoding limitation, not a new PBZ prohibition on Boolean tracks.

## Invalid stores generated by the script

Each fixture is a canonical example with a targeted change. A validator may
report more than one consequence of that change; exact error wording is not
part of the contract.

| Fixture | Expected rejection |
| --- | --- |
| `missing-reference` | R2: the `contig_id` array is absent. |
| `reference-wrong-dimension` | R4: `contig_id` is on the dimension `sequence`, not `contig`. |
| `duplicate-contigs` | R4: contig names are not unique. |
| `negative-length` | R6: negative reference length. |
| `short-position` | G2/D2: depth has eleven rows for a twelve-position reference/shared axis. |
| `unnamed-axis` | D1: a non-scalar dimension name is null. |
| `duplicate-samples` | D3: sample labels are not unique. |
| `global-binning` | G2: `bin_4` has three rows instead of four. |
| `floating-lengths` | R5: floating storage for reference lengths. |
| `genomic-axis-second` | G3: depth is stored as `(sample, position)`. |
| `two-genomic-axes` | G3: one measurement uses both `position` and `bin_4`. |
| `stored-position-coordinate` | G4: an explicit `position` coordinate array is persisted. |
| `noncanonical-bin-name` | G1: `bin_04` is not canonical. |
| `unlabeled-sample-axis` | D3: no coordinate array labels the sample dimension. |

The additional `unsupported-version` fixture has an unknown version marker.
Its expected outcome is **unsupported version**, not a claim about that unknown
format's validity.

## Other conformance cases

The example stores are a small set. The Rust tests also cover missing labels
after decoding, reference overflow, bad Zarr metadata, wrong reference
dimensions, repeated or empty dimension names, repeated values in other root
arrays, and `bin_1`.
