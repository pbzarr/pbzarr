# Releasing

Releases are driven by [release-please](https://github.com/googleapis/release-please)
from [Conventional Commit](https://www.conventionalcommits.org/) messages on `main`.
One version covers the whole repo: the `pbzarr` crate (crates.io), the `pbzarr`
Python wheel (PyPI) and the `pbz` CLI binaries (GitHub release) ship in lockstep.

## How a release happens

1. **Merge work to `main`** with Conventional Commit messages (`feat:`, `fix:`,
   `refactor:`, ...). release-please reads these to compute the next version and
   build the changelog.
2. **release-please opens (or updates) a release PR** titled `chore(main): release <version>`.
   It bumps the one version line in the root `Cargo.toml` `[workspace.package]`
   table (annotated `# x-release-please-version`), bumps the four workspace crates
   in `Cargo.lock`, and writes `CHANGELOG.md`. Every crate inherits that version
   via `version.workspace = true`, and the wheel reads it through
   `dynamic = ["version"]` in `pyproject.toml`, so nothing else needs a per-file
   bump. The `Cargo.lock` bump keeps `cargo build --locked` working on the release
   PR.
3. **Merge the release PR.** That creates the git tag and GitHub release
   (`releases_created == 'true'`), which triggers the publish jobs in
   `.github/workflows/release-please.yml`:
   - **build-wheels**: `.github/workflows/wheels.yml` builds abi3 wheels for
     linux x86_64 (manylinux_2_28, glibc 2.28 or newer) and a macOS universal2
     wheel (Intel + Apple Silicon) on the macos-15 Apple Silicon runner. It then
     installs each wheel, imports a d4 fixture, opens the store and reads a
     region.
   - **build-binaries**: starts `.github/workflows/release.yml` for the tag.
     That workflow is generated by [dist](https://axodotdev.github.io/cargo-dist/)
     from `dist-workspace.toml`. It builds `pbz` for linux x86_64 (in the
     manylinux_2_28 image, so glibc 2.28 or newer) and macOS arm64, runs an
     import and a `pbz stat` on a fixture (`test-binaries.yml`), and attaches
     the tarballs, their `.sha256` files and `pbz-installer.sh` to the GitHub
     release.
   - **publish-pypi**: uploads the wheels via PyPI Trusted Publishing
     (OIDC, environment `pypi`; no token stored).
   - **publish-crate**: `cargo publish -p pbzarr` via crates.io Trusted
     Publishing (OIDC; no token stored).

   The release builds do not use the build cache, so the published wheels and
   binaries always come from a clean build. CI caches dependency builds
   (`Swatinem/rust-cache` for cargo, sccache for the wheels) and saves the cache
   only from `main`. A pull request reads the cache from `main`.

   CI (`ci.yml`) runs the tests, the wheel and binary builds and the docs build
   on every push to `main` and on the release PR, so a broken build shows up
   before a release. On other pull requests, CI runs the tests and the docs build
   at once, but the wheel and binary builds wait in the `approve-builds` job for
   approval through the `pr-builds` environment. To run them, open the run and
   click **Review deployments**. Each new push to the PR asks again. If nobody
   approves, the builds do not run.

   The binary build in CI (`binaries.yml`) only builds and tests `pbz`. The
   release binaries come from the dist workflow. On a pull request, the dist
   workflow runs only its plan step, which checks that `release.yml` matches
   `dist-workspace.toml`.

   On a push to `main`, the docs job also deploys the site:
   `.github/workflows/docs.yml` builds it with Zensical (`pixi run -e docs
   docs-build`) and pushes `site/` to the `gh-pages` branch of
   `pbzarr/pbzarr.github.io`, which serves <https://pbzarr.github.io>. It uses
   the `DOCS_DEPLOY_KEY` secret. The site follows `main`, so it can show changes
   that are not in a release yet.

   release-please opens and updates the release PR with the default
   `GITHUB_TOKEN`, so GitHub holds those CI runs until someone approves them.
   Before you merge the release PR, click **Approve workflows to run** in its
   merge box and wait for CI to pass. release-please pushes to the PR each time
   `main` changes, and each push needs a new approval.
4. **Replace the release notes (optional).** release-please uses the generated
   changelog entry as the text of the GitHub release. To use curated notes,
   write them to a file outside the repo and replace the text:

   ```bash
   gh release edit v0.8.0 --notes-file notes.md
   ```

   This changes only the text. It does not run the publish jobs again.
   `CHANGELOG.md` keeps the generated entry.

## Crate and wheel stay linked

There is one version for the whole repo, and it lives in exactly one place:
`[workspace.package].version` in the root `Cargo.toml`. release-please tracks a
single root package (`"."`, `release-type: simple`) and bumps that annotated line
through its generic updater. Every member crate inherits it with
`version.workspace = true`, and the wheel derives it via `dynamic = ["version"]`
(maturin reads the binding crate's inherited version). The crate and the wheel
cannot drift, and both release from the same tag.

Merging the release PR fires one GitHub release, and that single event triggers
both `publish-pypi` (through `build-wheels`) and `publish-crate`. They run as
**independent parallel jobs**, not one atomic step: both publish the same version,
but if one fails the other can still succeed. Re-run a failed job from the Actions
tab; it republishes the same pinned version (a target that already exists on
PyPI/crates.io will reject the re-push, which is the expected safety net). You
cannot release just the wheel or just the crate, they always move together.

If the wheels fail to build for a version whose crate already published (so
the tag and GitHub release exist but PyPI is missing files), re-run the
`Release Please` workflow via **Run workflow** (`workflow_dispatch`) with the
`ref` input set to the tag (e.g. `v0.8.0`). That rebuilds the wheels off the tag
and runs `publish-pypi` through trusted publishing. `publish-crate` stays gated
on a fresh release and does not re-fire, so the crate is untouched.

If the binaries fail, run the `Release` workflow (the dist one) with the `tag`
input set to the tag:

```bash
gh workflow run release.yml --ref v0.9.0 -f tag=v0.9.0
```

To deploy the docs without a push to `main`, run the `Docs` workflow via **Run
workflow**. Leave the `ref` input empty to build from `main`, or set it to a tag.

## Package version and format version

The package version (for example 0.8.0) and the PBZ format version (0.5, written
as `pbz:version` in the root `zarr.json`) are different numbers. A package release
can keep the format version. Change the format version only when the spec changes.

PyPI has no 0.4.0 and no 0.6.0 wheels (the 0.6.0 release run failed).

## Supported platforms

- Wheels: Python 3.12 or newer; linux x86_64 with glibc 2.28 or newer (RHEL and
  Rocky 8+, Ubuntu 20.04+, Debian 10+) and macOS (Intel and Apple Silicon).
- `pbz` binaries: linux x86_64 with glibc 2.28 or newer, and macOS arm64.
- Older Linux (for example CentOS 7, glibc 2.17): build from source.

## Version pinning

release-please infers the next version from conventional commit history;
`.release-please-manifest.json` tracks the current released version. (The
one-off `release-as` pin used for the first release out of this repo has been
removed.)

## Crate publishing

`publish-crate` uses crates.io Trusted Publishing (OIDC via
`rust-lang/crates-io-auth-action@v1`), so no API token is stored in the repo. The
original blocker (the core crate's `d4` git dependency) is resolved: d4 import
moved to the unpublished `pbzarr-readers` crate, so `pbzarr` itself is git-dep-free
and `cargo publish -p pbzarr` succeeds.

`pbzarr-readers`, `pbz` and `pbzarr-python` stay unpublished (`publish = false`):
`pbzarr-readers` (and so `pbz`) carries git dependencies (the `d4` fork and
`rust-htslib` at a tag commit that is not on crates.io yet), and `pbzarr-python`
ships only as the wheel. `pbz` ships only as the release binaries. The importers
become publishable on crates.io only once their git dependencies are on crates.io
(or vendored) and `pbzarr-readers` flips to published.

## The zarrs patch

The root `Cargo.toml` has a `[patch.crates-io]` entry that replaces `zarrs` and
`zarrs_storage` with a fork commit. The fork fixes partial reads through the
`transpose` codec and makes `transpose` faster. A patch applies only to builds
from this repository (CI, the wheels and the `pbz` binaries). Users who add the
`pbzarr` crate from crates.io build against upstream `zarrs`, where a partial read
of a store that uses `transpose` fails (checked on zarrs 0.23.14). Remove the
patch when both fixes are in an upstream release.

## First-time setup checklist

- **PyPI:** add a Trusted Publisher for repo `pbzarr/pbzarr`, workflow `release-please.yml`,
  environment `pypi`. Retire the old `pbzarr-py` repo's release workflow so two
  repos don't both publish the `pbzarr` project.
- **GitHub:** the `Release Please` workflow needs `contents: write` + `pull-requests: write`
  (already set); the PyPI job needs `id-token: write` and the build-binaries job
  needs `actions: write` (both already set).
- **Docs site:** make `pbzarr/pbzarr.github.io` public (GitHub Pages on a private
  repo needs a paid plan). Make a deploy key:

  ```bash
  ssh-keygen -t ed25519 -N "" -C "pbzarr docs deploy" -f docs-deploy
  ```

  Add `docs-deploy.pub` to `pbzarr/pbzarr.github.io` (Settings, Deploy keys) and
  select **Allow write access**. Add the private key `docs-deploy` to
  `pbzarr/pbzarr` as the repository secret `DOCS_DEPLOY_KEY`. Then delete both
  key files. The first push to `main` (or a `Docs` run) makes the `gh-pages`
  branch. Then, in `pbzarr/pbzarr.github.io` (Settings, Pages), set the source to
  **Deploy from a branch**, branch `gh-pages`, folder `/ (root)`. Delete the old
  `.github/workflows/deploy.yml` in that repo, because it deploys the old site.
- **PR build approval:** create the `pr-builds` environment in `pbzarr/pbzarr`
  (Settings, Environments) and add yourself under **Required reviewers**. Leave
  **Prevent self-review** off, so that you can approve builds on your own PRs.
- **crates.io:** add a Trusted Publisher for the `pbzarr` crate: publisher type
  GitHub, repository `pbzarr/pbzarr`, workflow filename `release-please.yml` (leave
  environment blank, the job sets none). The crate `pbzarr@0.1.0` must already be
  owned by you (it is), since trusted publishing attaches to an existing crate.

## Changing the binary build

Edit `dist-workspace.toml`, then run `dist generate` to rewrite
`.github/workflows/release.yml`. Do not edit that file by hand; the dist
workflow fails its plan step when the file does not match the config. The
setup step that installs clang lives in `.github/build-setup.yml`. Use the same
dist version as `cargo-dist-version` in the config.

## Manual fallback

- Wheel: `pixi run build-wheel` produces a wheel in `target/wheels/`; upload with
  `twine`.
- Crate: `cargo publish -p pbzarr`.
