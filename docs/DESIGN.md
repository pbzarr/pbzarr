# PBZ design

PBZ is a small Zarr v3 convention for dense, per-base genomic data. The format supplies genomic interpretation and a flat track layout; Zarr supplies storage and codecs; xarray and Dask supply the Python read and analysis model.

pbzarr reads and writes format 0.5 (one root Dataset) only; see the [format 0.5 specification](../spec/README.md). Earlier contig-major, per-track, and wrapper-oriented designs are historical only.

## Rust reader

The Rust `pbzarr::Dataset` reads the
[format `0.5` root-Dataset schema](../spec/README.md).
It catalogs direct root arrays, validates reference and dimension coordinates,
and reads typed rectangular subsets. `read_raw` preserves physical values and
missing sentinels; `read_bool` decodes the supported Boolean encodings.
The module caches metadata and reference geometry, so callers must reopen after
external changes. It does not provide a concurrent-mutation snapshot.

CLI imports and appends write format `0.5`, and `pbz view` and `pbz stat`
read it. Python opens a `0.5` store as an `xr.Dataset` with `pbzarr.open`.
A format `0.4` store used one group per track. Every reader and writer, in
Rust, the CLI, and Python, refuses it with the same message. In Rust, the
error is `PbzError::LegacyFormat`.

The root `zarr.json` of a `0.5` store holds a consolidated metadata copy in
the zarr-python inline form. Every import, append, and Python write replaces
this copy as its last step. On a filesystem store, the Rust writer writes the
new root to a temporary file and renames it over `zarr.json`. Until that step,
the old copy shows the store as it was before the Rust write. A Python write
removes the copy while `to_zarr` runs. `Dataset::open` lists the store and does
not use the copy. `Dataset::open_readable` takes the variable list from the copy.

## Goals

PBZ makes per-base depth, signal, masks, and similar position-indexed data portable across Rust, Python, and ordinary Zarr tooling. It aims to preserve rank, keep genomic geometry explicit, and make xarray the normal Python read surface.

The format serves scalar signals as well as wide column tracks. A column axis can represent samples, strands, methylation contexts, or another declared label set; “cohort” is only the sample-specific case.

PBZ does not define a new container, codec, coordinate conversion layer, or query language. Coordinates are 0-based and half-open. Callers convert external 1-based formats at their own boundaries.

## Data model

A store holds one reference: ordered `(contig name, length)` pairs. Every track covers the whole reference, and the `position` dimension is all contigs concatenated in reference order.

A scalar track is a root array shaped `(position,)`. A 2D track is shaped `(position, column)`, where `column` is the declared dimension name. The labels of that dimension are a string array of the same name at the root, and tracks that share the dimension share its labels.

Every track declares a fill: the value at positions that no source covers. The Zarr fill value stores it. A track made with `TrackConfig` and no fill gets 0 for an integer dtype, NaN for a float dtype, and false for bool, with no `_FillValue`.

A null is the value that marks a missing position. It is fixed for each dtype, and nothing can change it:

| dtype | null |
|---|---|
| float32, float64 | NaN |
| int8, int16, int32, int64 | the type maximum |
| uint8, uint16, uint32, uint64 | the type maximum |
| bool | none |

`Dtype::null` gives this value. A track whose fill is `Fill::Na` stores the null as its Zarr fill value and declares it as the `_FillValue` attribute: NaN as base64 of the little-endian double, an integer as a JSON integer. `Null::attribute` builds this attribute. A track with a real fill declares no `_FillValue`. A bool track refuses `Fill::Na`. xarray decodes an integer track that declares a `_FillValue` to a float dtype, with NaN at the nulls. The float dtype is larger than the stored dtype:

| stored dtype | decoded dtype |
|---|---|
| int8, int16, uint8, uint16 | float32 |
| int32, int64, uint32, uint64 | float64 |

If you need nullable values, use a float dtype.

The importers use one rule: a position is missing unless the source says what its value is.

| importer | default fill | reason | `--fill` |
|---|---|---|---|
| d4 | 0 | d4 stores every base | no |
| BAM/CRAM | 0 | a base with no reads has depth 0 | no |
| BED3 mask (bool) | false | a base outside the intervals is not in the mask | no |
| bigWig | na | the format does not say what a gap means | yes |
| BED value column, not bool | na | the format does not say what a gap means | yes |
| BED value column, bool | false | as for a mask | yes (true or false) |

A gap in a bigWig or BED value column can be a real 0, for example in a bedGraph that leaves out zero regions, or it can be no value, for example in a methylation track. Give `--fill 0` (`fill` in Rust) when the gaps are 0. The bigWig reader reads NaN at every base that the file does not cover and writes only the covered bases, so the gaps get the fill. When the fill of an integer BED column is na, dtype inference keeps the type maximum free: data that reaches 255 in a column that would infer `uint8` infers `uint16`, and so on. A cell equal to the null of an explicit dtype stops the import with an error. `from_bigwig` takes the fill as an argument, and `BedImportOptions::fill` and `BedColumnRequest::fill` give it for BED. `build_bed_schema` applies its BED-level fill to each request that gives none. The import `Config` has no fill, so d4 and BAM/CRAM always fill 0. An append without a fill keeps the fill of the stored track. An append with a fill that differs from the stored fill is refused.

## Chunks and shards

By default, every track that an import creates is sharded and uses Blosc with zstd level 5 and byte shuffle. The inner chunk is 65,536 positions, and 1 column on a 2D track. A shard holds 1,024 inner chunks along positions (67,108,864 positions) and 16 columns. Each shard edge is capped at the axis extent rounded up to whole inner chunks. The CLI knobs are `--chunk` (positions per inner chunk), `--shard` (inner chunks per shard along positions) and `--shard-columns` (columns per shard). Python takes `chunk=`, `shard=` and `shard_columns=`. Rust takes `TrackConfig::chunk`, `shard` and `shard_columns`, and `TrackConfig::unsharded` makes a track with no shard; the CLI and Python do not expose an unsharded track. Existing tracks and append keep the stored layout.

Import entry points accept an explicit Zarr v3 codec spec (`--codecs` on the CLI, `codecs=` in Python) that replaces the whole default layout: a standard `codecs` list, with sharding expressed as a `sharding_indexed` codec and an optional `chunk_grid` member for the outer grid. Without `chunk_grid`, the outer grid is one inner chunk of positions by up to 16 columns. `--codecs` conflicts with the three layout knobs.

On a sharded track, the inner chunk is the shard's subchunk shape. Sharded writes append encoded subchunks through Zarr partial encoding instead of rewriting whole shards.

One import engine drives every format. A chunk is one inner position chunk, and it is the unit the engine writes. A span is a run of consecutive chunks, and it is the window one reader decodes in one pass. By default the engine sizes the span automatically: up to 4 million positions, and fewer when that leaves the workers short of pieces. A piece is one reader and one span. Each reader decodes each span once and fills every schema field in that one pass. Buffers still close and write per chunk, so the engine still skips an uncovered chunk inside a covered span. The engine pre-fills every buffer with the destination track’s declared fill value.

The worker that completes a buffer writes it. On an unsharded track, the buffer is one whole chunk. On a sharded track, the worker compresses the buffer and appends it to its shard exactly once, and a per-shard lock serializes the appends. The engine never writes a chunk that no reader covers. An absent chunk reads back as the fill value.

## Python API

The public namespace is `Reference`, `PbzError`, `open`, `create`, `write`, `RegionQuery`, `parse_region`, `reduce_regions`, `interval_mask`, `region`, `import_d4`, `import_bigwig`, `import_bed`, and `import_bam`. There is no store handle. Python reads through zarr-python and xarray. Rust is used only for imports and to parse region strings.

`pbzarr.open(source, *, tracks=None, chunks=..., storage_options=None)` returns the root of a format 0.5 store as one `xr.Dataset`. It checks the pbz convention entry and version, and refuses a format 0.4 store. It reads `pbz:version` "0.5" only and ignores `pbz:` attributes that it does not know. It reads the store metadata from the consolidated copy in the root `zarr.json` when the store has one, and lists the store when it does not. `pbzarr.write` refuses a store of another version. `tracks=` narrows the data variables and keeps the reference and label coordinates. By default each track is a Dask array. A track whose first dimension is genomic gets Dask chunks of about 128 MiB. A chunk holds all columns when one row of inner chunks of all columns fits in 128 MiB, and otherwise the most whole shards of columns that fit (at least one). Along positions, a chunk holds the most whole inner chunks that fit (at least one, at most the extent). When that is less than one shard, the count of inner chunks divides the inner chunks of a shard, so no Dask chunk crosses a shard edge; when it is more, it is whole shards. Other arrays are chunked by their stored shard (or chunk) shape. `chunks=None` gives lazy NumPy-backed arrays. The Dataset is a snapshot of the store at open time. A change in memory does not reach the store, and `close` and the context manager are those of `xr.Dataset`.

`pbzarr.open` also opens a zip store read-only. A local path is a zip store when it ends in `.zip` or is a regular file. The open reads the archive through a zarr-python `ZipStore` in mode `"r"` and takes the metadata from the consolidated copy. A zip store takes no `storage_options`. The `reference` coordinate, `region`, `reduce_regions`, and `interval_mask` work as on a directory store. Region tasks open the archive again by its path. `close` on the Dataset closes the archive. `write`, `create`, and each `import_*` function refuse a zip path, because a zip store is written once. Only `pbz import --zip` makes a zip store.

Every `xr.DataArray` and `xr.Dataset` from `open` carries a 0-d coordinate named `reference`. Its value is a short digest of the contig names and lengths. Its index, `ReferenceIndex`, holds the `Reference`. The coordinate has no dimension, so it stays through arithmetic, reductions, `concat`, `merge`, and `pickle`. When two objects with different references meet, xarray raises `AlignmentError`. `Reference.from_xarray(obj)` gives the reference back. The coordinate exists in memory only; no store holds it.

`Reference` is a mapping of contig name to length. `rows(query, dim="position")` maps one region to a slice of flat rows with the same rule as the Rust reader; on `bin_N` it gives the bins that intersect the region. `resolve(query)` gives the same region with contig-local `start` and `end` filled in: an open start is 0, and an open end is the contig end. Empty and out-of-range regions are refused. Select one locus with `pbzarr.region(ds["depth"], "chr1:100-200")`. `sel(position=...)` is reserved: with no genomic index, xarray treats it as row positions, and its meaning changes when the index arrives.

`pbzarr.region(obj, query, *, reference=None)` gives a view of one locus. `query` is a string such as `"chr1:100-200"` or `"chr1"`, a `RegionQuery`, or a `(contig, start, end)` tuple. A string goes through the Rust `RegionQuery` parser, the same parser as `pbz -r`. When the whole string is a contig name of the reference, the string is that contig. Only when there is no such name does the parser split the string on the last `':'`. Thus a contig such as `HLA-A*01:01:01` works. `parse_region` has no reference, so it always splits. `obj` is a whole-genome `xr.DataArray` or `xr.Dataset`, and the view has the same type. The reference and the full-length rule are the same as for `reduce_regions`. The function slices `position` and each `bin_N` dimension that is present through `Reference.rows`, so a Dataset view stays consistent. Variables with no genomic dimension pass through unchanged. The view carries the 0-d coordinates `region_contig`, `region_start`, and `region_end`. When `position` is present, the view also carries a numeric `pos` coordinate and the labels `"contig:pos"` as an indexed `position` coordinate. These positions are 0-based and contig-local, as `region_start` is. A `LocusIndex` on `position` holds the contig name and a range of positions. The labels and `pos` are made from it only when a caller reads the values, so a view of a whole contig adds no per-base memory. Two views of one contig align by label. Views of two contigs raise `AlignmentError` when they align, and `concat` of them keeps the labels in a plain index. `sel` takes exact labels, lists of labels, and label slices that include the end. The view carries the `reference` coordinate of the reference that was used. `region` and `reduce_regions` refuse a view that has a `position` dimension, because of its index, and a view that is shorter than the genome.

`pbzarr.reduce_regions(obj, intervals, reducer, /, *, reference=None, q=None, by=None, ddof=None, skipna=None)` reduces each interval along `position`. `obj` is an `xr.DataArray` or an `xr.Dataset`, and the result has the same type, with a `region` dimension first. Row `i` of the result is interval `i` of the input. Intervals can overlap, and each interval reduces all of its own rows. The result carries the coordinates `region_contig`, `region_start`, and `region_end` on `region`. The reference comes from the `reference` coordinate. `reference=` overrides it, or gives it when the input has no coordinate, for example a Dataset from `xr.open_zarr`. Each genomic dimension must have its full length; a sliced input is refused. `position` can be at any place in the dimensions. On a Dataset, the variables with `position` are reduced. Variables with no genomic dimension and the coordinates that are not on a genomic dimension pass through unchanged. Variables on a `bin_N` dimension are left out, and one warning names them. Coordinates on `position` are dropped. The result carries the `reference` coordinate of the reference that was used, and it has no Dataset attributes. A track may have at most one dimension in addition to `position`. Intervals may be a dataframe, three arrays, rows, or a list of region strings. A dataframe needs one `contig`, `chrom`, or `#chrom` column, a `start` column, and an `end` column. The reducers are `mean`, `sum`, `min`, `max`, `count`, `std`, `var`, `median`, `quantile` (needs `q=`, a number or a list), and `summit` (needs `by=`). `ddof=` applies to `std` and `var`. `skipna=` (default True) ignores NaN values. A reducer refuses an option that it does not use, and an unknown keyword raises `TypeError`. `summit` gives, for each interval and column, the values of all tracks at the row where the `by` tracks are highest (compared in order; the first row wins a tie), and the contig-local `summit_position` of that row. The function sorts the intervals by position and puts them in batches with a limit on bytes and on Dask chunks. Each batch is one task. The task reads only the rows of its intervals, as one range or as exact rows when the intervals are far apart, and reduces each interval with NumPy. A track that `pbzarr.open` read directly from a store is read again from the store in the task. For an integer track with an integer `_FillValue`, the task reads the raw integers, so it does not hold the rows in the larger decoded float dtype. The reducer treats a value equal to the null as missing, as NaN in the decoded track: `count` leaves it out, and the other reducers skip it when `skipna=` is True. With `skipna=False`, a region that holds a null gives NaN. `summit` ranks a null lowest, and a selected null is NaN. Only the per-region result changes to the decoded float dtype, so the result is the same as for the decoded track. `pbzarr.region` gives decoded values, with NaN at the nulls. Any other track, for example a transformed or NumPy-backed one, is sliced directly. With Dask input the result is lazy; with NumPy-backed input (`chunks=None`) it is computed at once. The function does not detect a full-length reorder of `position`, such as `roll` or `sortby`.

`pbzarr.interval_mask(obj, intervals, /, *, reference=None)` gives a bool `xr.DataArray` over `position`. A value is True inside any interval and False outside. `obj` is a whole-genome `xr.DataArray` or `xr.Dataset` with a `position` dimension. The intervals take the same forms as for `reduce_regions`, and they can overlap. The reference and the full-length rule are the same as for `reduce_regions`. The mask is a Dask array with the `position` chunks of `obj`, or with the Dask default chunks when `obj` is not chunked. Each chunk is computed from the intervals when it is read, so a whole-genome mask holds no whole-genome array. The mask carries the `reference` coordinate of the reference that was used.

`pbzarr.write(target, variables, *, encoding=None, storage_options=None)` adds `xr.DataArray` values as new root arrays through `to_zarr(mode="a")`. `target` is a path, a URL, or a Dataset from `open`; for a Dataset, the store is `ds.encoding["source"]`. `variables` is a mapping of name to `xr.DataArray`, and an `xr.Dataset` is such a mapping. The write reads the store metadata when it is called and checks the values against it. It keeps no cache. It never changes an existing array, and it returns the store opened again. The Dataset passed as `target` does not change. A genomic dimension must come first and span the reference. Shared non-genomic dimensions must match the store's labels. A new dimension needs a label coordinate that lies on that dimension only. The write finds the `reference` coordinate by name, with or without its index, and compares it with the reference of the store. A different reference raises `AlignmentError`. Then the write drops the coordinate. A value without the coordinate is accepted when its genomic length matches. Tracks are numeric or bool. A variable with no genomic dimension can also hold strings, which are stored as variable-length UTF-8. The write saves the non-dimension coordinates of the values, such as `sample_group(sample)`. A coordinate with the name of a store array must have the same dimensions and labels as that array. The write drops every 0-d coordinate, for example `sample` after `isel(sample=0)` or `quantile` after `quantile(0.5)`. The write refuses a coordinate over `position` or `bin_N`. The write keeps the root attributes, drops `pbz:summary` and the zarrs provenance attribute from the values, refuses other `pbz:` attributes and attributes that change decoding, and writes `_FillValue` only when the caller declares one in `encoding=`. Track names must not be genomic dimension names or `reference`. It removes the arrays it created if the write fails. A new variable whose first dimension is `position` and that has 1 or 2 dimensions gets the import layout: inner chunks of 65,536 positions (and 1 column), shards of 1,024 inner chunks capped at the extent rounded up to whole inner chunks (and min(16, width) columns), and Blosc zstd level 5 with shuffle. When `encoding=` for the variable gives `chunks`, `shards`, or `compressors`, xarray chooses the layout instead. The write rechunks a Dask-backed value with the import layout to whole shards, so each write task holds one shard; a shard of 16 `int32` columns is 4 GiB. Other written variables use the Zarr and xarray defaults unless `encoding=` says otherwise. The write checks the store by listing it, not by reading the consolidated copy. As its last step, it replaces the consolidated copy with `zarr.consolidate_metadata`.

`create(destination, *, reference, storage_options=None)` creates an empty store at a local path for `write` and returns it opened as an `xr.Dataset`. It does not create remote stores yet: a URL destination or a `storage_options` value other than `None` raises `ValueError` before anything is written. `import_d4`, `import_bigwig`, `import_bed`, and `import_bam` follow the store-creation rule of the CLI (see [CLI](#cli)). They write local stores only, and return a report dictionary with `positions`, `chunks_written`, `chunks_skipped`, `bytes_written`, and `wall_seconds`. They share the `dim`, `threads`, `decode_chunks`, `chunk`, `shard`, `shard_columns`, `codecs`, and `progress` keyword arguments. `chunk` is the positions per inner chunk (default 65,536), `shard` is the inner chunks per shard along positions (default 1,024), and `shard_columns` is the columns per shard of a 2D track (default 16). `codecs` conflicts with the three layout keywords. `import_bam` takes the CRAM reference FASTA as `fasta=`. Each import takes `sources` as a path, a `(path, label)` tuple, or a list of them. A `(path, str)` tuple is always one labeled source. As in the CLI, all sources have labels or none do. A missing source file or store raises `FileNotFoundError`, and a bad argument raises `ValueError`. Other failures raise `PbzError`. With `progress=True`, an import writes plain progress lines to Python `sys.stderr`, so Jupyter shows them in the cell output. Ctrl-C stops an import: the import stops its workers, removes a store that it created, and raises `KeyboardInterrupt`. The bindings choose the Python exception from the kind of the Rust error, not from its message. Every call from Python into the bindings uses keyword arguments.

`import_bigwig` and `import_bed` take `fill=`, as `--fill` in the CLI: a number, `True` or `False` for a bool track, or `"na"`. `None` gives the default of the importer. A bad fill raises `ValueError`. The bindings send the fill as text and parse it with `Fill::parse`.

`import_bed(destination, sources, *, genome=None, ...)` covers every BED shape in one call, mirroring `pbz import bed`: `track=`/`column=`/`dtype=` import one BED column as one track, and `schema=` maps BED columns to entries, one track per entry. An entry is a dtype string, `None`, or a dict with the optional keys `"track"`, `"dtype"`, and `"fill"`. An entry without a track takes the header name, an entry without a dtype is inferred, and an entry without a fill takes `fill=`. A column is a header name or a 1-based column number. A numbered column must be 4 or more and needs a track name. `build_bed_schema` in `pbzarr-readers` holds these rules, and the CLI `--schema` uses the same function, with the same default of 1000 sampled records for dtype inference. Any 2D output, over several sources or over several BED columns of one wide track, requires `dim=`. `genome=` is needed only to create the store.

## Rust API

`Dataset::create(path, reference)` and `Dataset::open(path)` operate on filesystem stores. `create_with_storage` and `open_with_storage` take any synchronous readable, writable, listable Zarr storage handle. `Dataset::open_read_only(path)` opens a store for reads only. It lists a directory store, as `Dataset::open` does. A file that starts with a zip local file header opens through `Dataset::open_zip(path)`. `open_zip` reads the archive with `zarrs_zip` and takes the variable list from the consolidated copy in the root `zarr.json`. `is_zip_store(path)` gives this test. `Dataset::open_readable(storage)` takes any readable storage handle. It does not list or write the storage. It takes the variable list from the consolidated copy, so the store must have the copy. A read-only Dataset refuses every import and append. `Dataset::create_zip(path, reference)` creates a store that becomes one zip file. Imports into it work as for a directory store. `Dataset::close` writes the archive and moves it to `path`. Until then, the archive is a temporary file beside `path`. A Dataset that is dropped before `close` removes that file. The archive is Zip64, every entry is STORED, and the root `zarr.json` is the first entry of the central directory. Each data key is written once. A second write of a data key is an error. An erase of a key that was never written does nothing. The `zarr.json` keys stay in memory until `close`. One mutex guards the archive, so data entries are appended by one writer at a time; the engine workers still compress in parallel. `pbz view`, `pbz stat`, `pbz info`, and `pbz validate` use the read-only open. `Dataset::stored_size(name)` gives the bytes and the number of stored objects of one array, without its `zarr.json`. It gives `None` for a Dataset from `open_readable`, which cannot list keys. `TrackConfig::new(dtype)` configures scalar or 2D tracks with generic columns, chunking, optional sharding, the fill (`Fill::Value` or `Fill::Na`), and optional description or source metadata. `Dataset::read_region<T>` reads one region of a track at full column width.

`Reference` holds named contigs and derives flat offsets. Regions are 0-based and half-open.

The crate root exports `Dataset`, `Reference`, `GenomicAxis`, `Contig`, `Region`, `TrackConfig`, `Fill`, `Null`, `Import`, `Measurement`, and the error type `PbzError`. Three modules stay public: `pbzarr::import` holds the import configuration and targets, `pbzarr::io` holds the `ValueReader` trait for reader crates, and `pbzarr::stat` holds the region statistics.

An import refuses a track or dimension name that the store keeps for itself: `position`, any `bin_N`, `contig`, `contig_id`, `contig_length`, `contig_md5`, and `reference`.

The format-agnostic import engine drives any `ValueReader`. A reader exposes an ordered schema of named dtype fields. `read_into` fills one sink per field for one contig window in a single decode pass. `read_windows` decodes a run of adjacent windows and reports which windows have no data, so the engine can skip them. `fork` gives each worker its own handle. Each reader has a pool of handles. The pool starts with the reader itself and grows by forks up to its share of the handle budget. The budget counts every open handle, so a run holds one handle per reader at minimum.

`Import::from_readers(..)` starts a run: the builder chains `into_dataset(..)`, an optional axis statement (`fields_as_tracks()`, `fields_as_columns()`, or `readers_as_columns()`), and `config(..)`, and `run()` returns a `Report`. The public configuration surface is `pbzarr::import::{Config, ConfigBuilder, Report, Source}`. `Config` is the one options type: the engine reads the worker count, `decode_chunks`, the progress hook, and the cancel flag (a set flag fails the run with `PbzError::Cancelled`), and the format entry points read the track sizes. The CLI and the Python bindings build it with `ConfigBuilder`, where an unset field keeps the default. Reader crates provide d4 (`int32`), bigWig (`float32`), BED (schema-typed columns), and BAM/CRAM (`int32` depth and composition counts) sources. Python exposes them through the destination-oriented writers.

## Interoperability

PBZ uses standard Zarr v3 groups, arrays, codecs, and variable-length UTF-8 strings. Released xarray opens a format 0.5 store directly through `xr.open_zarr`. A float `_FillValue` must be base64 of a little-endian double, as xarray writes it. `xr.open_zarr` fails for the whole store when a float array has a numeric `_FillValue`, so no pbzarr writer writes one. The Rust reader marks such an array as an unsupported encoding, and `pbz validate` reports it. `pbzarr.open` refuses such a store with a `PbzError` that names the array. The consolidated copy in the root `zarr.json` lets `consolidated=True` find every array, also for a reader that cannot list the store.

`pbzarr.open` adds identity and reference checks, Dask chunk defaults, region selection, region operations, and validated writes.

Cross-language validation (`pixi run validate-roundtrip`) imports d4 fixtures with Rust, opens the stores through released xarray and `pbzarr.open`, compares variables, dimensions, dtypes, root attributes, values, and a contig boundary, then writes a derived track from Python and checks the store with the Rust `check_dataset` example.

The Python package needs Python 3.12 or later. Its dependency floors in `pyproject.toml` are the versions that the pixi lock tests. The public API has type annotations, and the package ships `py.typed`. `pbzarr.__version__` comes from the installed package metadata. `pixi run wheel-test` builds the wheel, installs it (not editable) into a temporary venv, imports a d4 fixture, opens the store, and reads a region.

## CLI

The `pbz` CLI ships `import d4`, `import bigwig`, `import bed`, `import bam`, the same four `append` subcommands, `view`, `stat`, `info`, and `validate`. Every command takes the store path as its first positional argument (`STORE`) and names a track with `--track`. On `view` and `stat`, `--track` is optional when the store has one track, and `-o`/`--output` names the output file. The import and append subcommands take positional `PATH[:LABEL]` sources after `STORE`, or `--file-list`, plus `--dim`, `--codecs`, `--decode-chunks`, and `-t`/`--threads`. The import subcommands also take `--chunk N` (positions per inner chunk), `--shard N` (inner chunks per shard along positions) and `--shard-columns N` (columns per shard of a 2D track). A source splits on its last `:` only when the text after it has no `/` or `\`, so URLs and Windows paths stay whole. The default label is the file name without its format extension, and a `.gz` or `.bgz` suffix goes with the extension before it (`s1.bed.gz` gives `s1`). `Source::label` holds this rule, so the CLI and the Python imports give the same labels. `Source::check_labels` refuses a source list in which only some sources have labels. Relative paths in a `--file-list` start from the directory of the list file. `import bigwig`, `import bed`, `append bigwig`, and `append bed` take `--fill VALUE|na`. The value is a number, `true` or `false` for a bool track, or `na`. `import bed` also takes a `--schema` TSV. Its rows are `BED_COLUMN[<TAB>TRACK[<TAB>DTYPE[<TAB>FILL]]]`, and an empty or absent `FILL` takes `--fill`, else the default. `import bed --emit-schema BED` prints a schema TSV for one BED file and takes no `STORE`. Its `FILL` column is `na` for a value column and `false` for a bool column. `import bam` takes the CRAM FASTA as `--fasta`. Its `--exclude-flags` takes a decimal number, a `0x` hex number, or comma-separated samtools flag names; the default is `UNMAP,SECONDARY,QCFAIL,DUP`. `--stat` and `--dtype` take a fixed list of values, which the help shows. `-v`/`--verbose` and `-q`/`--quiet` are global flags, so they work before or after the subcommand. An import or append writes one summary line to stderr, and `-q` hides that line and the progress display. stdout carries only data. At startup, the CLI raises the soft open-file limit to the hard limit. When `STORE` does not exist, an import creates a format 0.5 store. The import first checks that all sources have the same contigs, then takes the store reference from them. If the import fails, it removes the new store. When `STORE` exists, the import adds tracks to that store, and the sources must match the store reference. The import refuses a format 0.4 store. The import refuses a track name that the store already uses. BED files have no contig lengths, so `import bed` needs `--genome` only to create a store; an existing store gives its own lengths. In Rust, `Target::Path` holds this rule, and `store_reference` gives the contig list for BED.

`--zip`, or a `STORE` path that ends in `.zip` in any case, writes a new zip store through `Target::Zip`. The path must not exist. `Target::Zip` creates the store with `Dataset::create_zip`, takes the reference from the sources, runs the import, and calls `close`. A failed import drops the Dataset, which removes the temporary file. Every track gets the default layout of a directory store. `Target::Zip` refuses an unsharded track and codecs that have no `sharding_indexed` codec. `Target::Path`, `store_reference` and `pbz append` refuse an existing zip store, because nothing adds tracks or columns to it.

`view` exports one track as bedGraph-like TSV: `chrom`, `start`, `end`, then one value column per track column, with equal-value runs collapsed. A null prints as `NaN` for every dtype. Positions where all selected columns are null are skipped. It subsets rank-2 columns with `-c`/`--columns` and writes BGZF when the output path ends in `.gz`. `view` reads only the inner column chunks that hold the selected columns, and its batches start and end on the inner position chunk grid. `view` and `stat` read a track through `Measurement::root`, which refuses a track whose first dimension is not `position` (a `bin_N` track included), a track with more than one other dimension, and a `_FillValue` that is not a null: a float `_FillValue` must be `NaN`, and an integer `_FillValue` must be a value of the track dtype. `Measurement::null` gives the null of the track: NaN for a float track, the `_FillValue` for an integer track, and `None` when an integer track declares none. `stat` skips nulls in every statistic, and the median of a region with only nulls is `NaN`. `VariableInfo::null` gives the null that the `_FillValue` declares. The help and the README give these limits.

`view` and `stat` select regions with `-r`/`--region CHROM:START-END`, which can repeat, and `-R`/`--regions FILE.bed`. Coordinates are 0-based and half-open, as in BED. `-r` takes the `RegionQuery` syntax, so `CHROM` alone is the whole contig. Commas in coordinates are ignored. When the whole value is a contig name, the value is that contig, as in samtools. Only when there is no such name is the value split on the last `':'`. Each region goes through `Reference::region`, which refuses an end past the contig. The `-r` regions come first, in the given order, then the BED regions in file order. Without a region, the commands cover the whole genome: `view` writes rows in genome order and `stat` writes one row per contig. `view` collapses runs only inside one region. A closed stdout, as from `pbz view | head`, ends `view` and `stat` with exit code 0 and no error.

`info` opens the store read-only and prints the format version, the reference, the dimension sizes, and one row per variable: role (track, coordinate, or other), dtype, dimensions, shape, inner chunk shape, shard shape, chunk codec names, Zarr fill value, declared null (`none` when there is no `_FillValue`), stored bytes, and object count. The byte and object counts come from `Dataset::stored_size` and leave out `zarr.json`. `--json` prints the same fields as one JSON object. Before `view`, `stat`, `info`, or `validate` opens a store, the CLI checks that the path exists. Library error messages do not start with a format rule code; a `ValidationIssue` keeps the code in its `rule` field. `validate` opens the store read-only and runs `Dataset::validate`. An open error that the format rules cover, such as a missing convention identity or an unsupported version, becomes one problem. The text output gives each problem without its rule code; `--json` keeps the code in a `rule` field. The exit code is 0 only for the status `valid`; `invalid`, `incomplete`, and `unsupported_version` exit with 1. The `check_dataset` example stays the conformance probe for `scripts/validate_dataset.py`.
